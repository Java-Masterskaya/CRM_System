# Техническая спецификация — CRM «Заявки на обработку данных»

**Версия:** 2.0 · Дополняет [ТЗ](TZ.md). ТЗ отвечает «что и зачем», спецификация — «как».

---

## 1. Стек

| Слой | Решение | Почему |
|---|---|---|
| Язык | Java 21 | LTS; records, sealed-типы и pattern matching упрощают модель домена |
| Фреймворк | Spring Boot 3.x | Стандарт индустрии, вся команда его знает |
| Сборка | Gradle (Kotlin DSL) | Требование проекта |
| БД | PostgreSQL 16 | Требование ТЗ |
| Доступ к данным | Spring Data JPA | Скорость разработки; сложные выборки — на нативных запросах |
| Миграции | Flyway | Простой, предсказуемый, версионируемый |
| Безопасность | Spring Security | Stateless-конфигурация + JWT |
| Документация | springdoc-openapi | Генерация из кода, не ручная |
| Метрики | Micrometer + Actuator | Стандартный экспорт в Prometheus |
| Тесты | JUnit 5, Testcontainers, ArchUnit | Реальная БД в тестах, автопроверка границ |
| Почта | Spring Mail; MailHog локально | Ловим письма локально без внешнего SMTP |

**Не используем:** кэш (Redis), реактивный стек (WebFlux), Lombok на публичных DTO
(генерируемые API-модели должны быть читаемыми), `ddl-auto` кроме `validate`.

## 2. Архитектура

### 2.1 Форма
**Модульный монолит, один Gradle-модуль, разбиение по функциональным пакетам** (package-by-feature).

Почему не мультимодульный Gradle: при 10 разработчиках выигрыш от изоляции сборки не окупает
постоянных конфликтов в build-файлах и роста времени сборки. Границы обеспечиваются
правилами пакетов и автотестами, а не структурой сборки. При росте проекта переход на
мультимодульность возможен без переписывания — пакеты уже разделены.

### 2.2 Пакеты и владение

```
crm/
├── common/          общие типы: ошибки, пагинация, базовые сущности, время
├── tenant/          арендаторы, контекст арендатора, изоляция
├── security/        аутентификация, токены, права, конфигурация доступа
├── user/            пользователи, роли, профили
├── request/         заявки: модель, жизненный цикл, история, аудит
├── assignment/      назначение исполнителей, очередь работ
├── sla/             политики сроков, рабочий календарь, эскалации
├── comment/         комментарии
├── attachment/      вложения, клиент медиа-сервиса
├── notification/    шаблоны, отправка, статусы доставки
├── outbox/          надёжная доставка исходящих событий
├── analytics/       отчёты и агрегаты
├── integration/     вебхуки, импорт, экспорт
└── platform/        конфигурация, наблюдаемость, планировщик
```

Каждый пакет — зона ответственности одной пары разработчиков. Это же — карта владения
для code review.

### 2.3 Правила границ (проверяются ArchUnit)
- Пакет предоставляет наружу **только** свой публичный сервис-интерфейс и DTO.
  Сущности, репозитории и внутренние классы наружу не выходят.
- Контроллеры не обращаются к репозиториям напрямую.
- `common` не зависит ни от одного функционального пакета.
- Циклических зависимостей между пакетами нет.
- Взаимодействие между слабо связанными пакетами — через события приложения, не прямой вызов.

Нарушение границы должно ронять сборку, а не всплывать на ревью.

### 2.4 Слои внутри пакета
```
request/
├── api/         контроллеры, DTO запросов и ответов, маппинг
├── domain/      сущности, перечисления, правила жизненного цикла
├── repository/  доступ к данным
├── service/     бизнес-логика, транзакции
└── event/       события, публикуемые наружу
```

## 3. Ключевые технические решения

### 3.1 Изоляция арендаторов
Многоуровневая защита — одного механизма недостаточно.

1. **Контекст запроса.** Идентификатор арендатора извлекается из токена и помещается в
   контекст текущего запроса. Обязательна гарантированная очистка контекста после запроса —
   иначе значение утечёт в следующий запрос через переиспользуемый поток.
2. **Автоматическая фильтрация.** Фильтр по арендатору применяется на уровне доступа к
   данным централизованно, а не повторяется в каждом запросе.
3. **Защита на уровне БД** *(желательно)*. Политики Row Level Security в PostgreSQL как
   последний рубеж — даже ошибочный запрос не вернёт чужие строки.
4. **Тесты.** Отдельный набор тестов на каждый эндпоинт: пользователь арендатора A не
   получает данные арендатора B.

Идентификатор арендатора **никогда** не принимается из тела, пути или параметров запроса.
Единственное исключение — регистрация и вход, где токена ещё нет: там клиент передаёт
`tenantSlug`, и он используется только для поиска арендатора в этой операции.

### 3.2 Аутентификация и токены
- Access-токен — короткоживущий (порядка 15 минут), содержит идентификатор пользователя,
  арендатора и набор прав. В базу за правами на каждый запрос не ходим.
- Refresh-токен — долгоживущий (порядка 7 дней), хранится в БД **в виде хэша**, не в открытом виде.
- **Ротация с обнаружением повторного использования.** При обмене старый токен помечается
  использованным. Повторное предъявление уже использованного токена трактуется как кража:
  вся цепочка токенов пользователя отзывается.
- Выход отзывает refresh-токен; истёкшие записи периодически удаляются.
- Ключ подписи — только из окружения.

### 3.3 Права доступа
- Право — строковый идентификатор вида `REQUEST_READ_ALL`, `REQUEST_STATUS_CHANGE`, `USER_MANAGE`.
- Роль — набор прав, задаётся данными (миграцией), не кодом.
- Проверка на уровне метода по праву, не по роли. Роли в коде не «зашиваются».
- Проверка владения объектом — в сервисе, отдельно от проверки права.
- Конфигурация доступа — запрет по умолчанию: всё, что не разрешено явно, закрыто.

### 3.4 Жизненный цикл заявки
- Матрица допустимых переходов задаётся декларативно в одном месте — таблица «из какого
  статуса в какие можно». Разнесённые по коду проверки `if (status == ...)` запрещены.
- Смена статуса, запись истории и постановка исходящего события — **одна транзакция**.
- Отправка письма и вызов вебхука — **вне** транзакции, отдельным процессом.
- Правило «кто имеет право на переход» — отдельно от правила «переход технически возможен».

### 3.5 Надёжная доставка (outbox)
Проблема: письмо нельзя отправлять внутри транзакции — если транзакция откатится, письмо
уже ушло; если отправка упадёт, откатится бизнес-операция.

Решение: событие записывается в таблицу исходящих сообщений в той же транзакции, что и
изменение данных. Отдельный фоновый процесс забирает необработанные записи и доставляет
их, помечая результат. При сбое — повтор с нарастающей задержкой, после исчерпания попыток
запись помечается неуспешной и остаётся для разбора.

Требования к процессу: забор порциями с блокировкой (два экземпляра приложения не должны
взять одну запись), идемпотентность, корректное завершение при остановке приложения.

### 3.6 Конкурентный доступ
- На заявке — поле версии; при сохранении устаревшей версии операция отклоняется с
  понятной ошибкой.
- Операция «взять в работу» должна быть атомарной: двое одновременно нажавших — один
  получает заявку, второй получает отказ, а не оба «успех».

### 3.7 Расчёт SLA
- SLA-политика привязана к типу заявки и приоритету, задаёт срок первого ответа и срок решения.
- Расчёт ведётся в рабочих часах по календарю арендатора: часы работы по дням недели плюс
  список нерабочих дат.
- Время в статусе `ON_HOLD` из срока вычитается. Хранится накопленная длительность паузы.
- Фоновая проверка просрочек — идемпотентная: повторный запуск не шлёт эскалацию заново.

### 3.8 Обработка ошибок
- Единый формат ответа об ошибке на весь API, с машиночитаемым кодом и человекочитаемым
  описанием; для ошибок валидации — список полей с причинами.
- Рекомендуется стандартный формат Problem Details (RFC 7807) вместо самописного.
- Обработка — централизованно, в одном месте, а не try/catch в контроллерах.
- Сообщения об ошибках не раскрывают внутреннее устройство: ни стектрейсов, ни SQL, ни
  имён таблиц наружу.

### 3.9 Пагинация и поиск
- Списки по умолчанию — постраничная навигация с ограничением максимального размера страницы.
- Для реестра заявок при больших объёмах — навигация по курсору (keyset), а не по смещению:
  запрос с большим смещением деградирует.
- Поиск по тексту — средствами PostgreSQL; отдельная поисковая система в v1 не вводится.
- Каждый поддерживаемый фильтр обязан иметь индекс. Проверяется планом запроса, а не на глаз.

### 3.10 Наблюдаемость
- Проверки живости и готовности разделены: готовность учитывает доступность БД.
- Метрики: технические (частота и длительность запросов, ошибки, пул соединений, фоновые
  задачи) и продуктовые (создано заявок, переходы по статусам, просрочки, отправлено писем).
- Логи — структурные, в машиночитаемом формате, с уровнем и контекстом.
- Сквозной идентификатор запроса генерируется на входе (или принимается из заголовка) и
  добавляется во все записи логов этой операции и в ответ клиенту.
- **В логи не попадают:** пароли, токены, содержимое писем, персональные данные.

## 4. Схема данных

### 4.1 Соглашения
- Имена таблиц и колонок — в нижнем регистре через подчёркивание, таблицы во множественном числе.
- Первичные ключи — UUID; генерируются приложением, а не базой.
- У всех прикладных таблиц: `tenant_id`, `created_at`, `updated_at`.
- Мягкое удаление там, где данные нельзя терять (заявки, пользователи) — признак удаления,
  а не физическое удаление.
- Внешние ключи объявляются явно; каскадное удаление применяется осознанно.
- Денежных величин нет; временные метки хранятся в UTC.

### 4.2 Основные таблицы
| Таблица | Назначение |
|---|---|
| `tenants` | Арендаторы |
| `tenant_settings` | Настройки арендатора, включая рабочий календарь |
| `users` | Пользователи; email уникален в пределах арендатора |
| `roles`, `permissions`, `role_permissions`, `user_roles` | Модель доступа |
| `refresh_tokens` | Хэши refresh-токенов, срок, признак использования и отзыва |
| `request_types` | Справочник типов заявок арендатора |
| `requests` | Заявки; включает статус, приоритет, исполнителя, сроки, версию |
| `request_status_history` | История переходов |
| `request_audit_log` | Журнал изменений полей |
| `request_comments` | Комментарии с признаком видимости клиенту |
| `request_attachments` | Ссылки на объекты медиа-сервиса |
| `sla_policies` | Политики сроков |
| `holidays` | Нерабочие даты |
| `outbox_events` | Исходящие события для надёжной доставки |
| `notifications` | Уведомления и статус их доставки |
| `webhook_subscriptions`, `webhook_deliveries` | Вебхуки и попытки доставки |

### 4.3 Индексы — обязательный минимум
- `requests`: по арендатору со статусом, по исполнителю, по клиенту, по сроку решения,
  по признаку просрочки, по дате создания.
- `users`: уникальный по паре арендатор + email.
- `refresh_tokens`: по хэшу токена, по пользователю.
- `outbox_events`: по статусу и времени следующей попытки.
- Полнотекстовый индекс по теме и описанию заявки.

### 4.4 Правила миграций
- Один PR — одна миграция. Файлы именуются по дате и времени создания, а не по
  сквозному номеру: при 10 разработчиках сквозная нумерация гарантированно порождает
  конфликты.
- Миграции **неизменяемы** после попадания в основную ветку. Исправление — только новой миграцией.
- Каждая миграция обратимо совместима: сначала добавляем, потом переключаем код, потом
  удаляем старое — тремя отдельными шагами, а не одним.
- Тестовые данные — отдельно от структурных миграций, применяются только в локальном профиле.

## 5. Соглашения по API

### 5.1 Структура путей
```
/api/v1/auth/**      — регистрация, вход, обновление и отзыв токенов (без авторизации)
/api/v1/client/**    — клиентский контур, роль CLIENT
/api/v1/admin/**     — административный контур, роли OPERATOR и ADMIN
/api/v1/system/**    — служебный контур: подключение арендатора; секрет из окружения, не JWT
/actuator/**         — служебные эндпоинты, наружу не публикуются
```
Клиентский и административный контуры реализуются **разными контроллерами**, даже если
работают с одной сущностью. Причина: у них разные права, разные наборы полей в ответе и
разная скорость изменения. Общий контроллер с ветвлением по роли — источник ошибок доступа.

### 5.2 Правила
- Ответы клиентского контура **не содержат** внутренних полей: внутренних комментариев,
  идентификаторов операторов, служебных пометок.
- Коды состояния используются по назначению: создание — 201, успешная операция без тела —
  204, ошибка валидации — 400, нет аутентификации — 401, нет прав — 403, не найдено или
  чужое — 404, конфликт состояния или версии — 409, превышен лимит — 429.
- Изменяющие операции принимают ключ идемпотентности; повтор с тем же ключом возвращает
  прежний результат.
- Формат даты и времени — единый по всему API, с указанием часового пояса.
- Контракт фиксируется до реализации: сначала согласованное описание эндпоинта, потом код.

## 6. Конфигурация и среды

- Профили: `local` (разработка), `test` (автотесты), `prod`.
- Все секреты — из переменных окружения. В репозитории лежит только файл-образец без значений.
- Локальный запуск: приложение, PostgreSQL и почтовая заглушка поднимаются одной командой.
- Значения по умолчанию безопасны: если переменная не задана, приложение не стартует с
  небезопасной настройкой, а падает с понятным сообщением.

**Обязательные переменные окружения:** параметры подключения к БД, ключ подписи токенов,
сроки жизни токенов, параметры SMTP, адрес и токен медиа-сервиса (gRPC), секрет служебного
контура.

## 7. Тестирование

| Уровень | Что покрывает | Требование |
|---|---|---|
| Модульные | Правила жизненного цикла, расчёт SLA, права | Быстрые, без поднятия контекста Spring |
| Срезовые | Контроллеры и конфигурация доступа | Обязательно проверяют коды 401/403/404 |
| Интеграционные | Сценарии на реальной БД в контейнере | Общий контейнер на прогон, не на тест |
| Архитектурные | Границы пакетов, запрет зависимостей | Падают при нарушении правил |
| Нагрузочные | Реестр заявок на объёме | Профиль нагрузки описан отдельно |

**Обязательные наборы тестов** (без них задача не принимается):
- Изоляция арендаторов — на каждый эндпоинт, возвращающий данные.
- Разграничение прав — на каждый защищённый эндпоинт.
- Матрица переходов статусов — все допустимые и все запрещённые.

Правило именования тестов: описывается сценарий и ожидаемый результат, а не имя метода.
Тест обязан падать по осмысленной причине — проверяется временной поломкой кода.

## 8. Процесс разработки

### 8.1 Ветвление и ревью
- Основная ветка защищена: прямой push запрещён.
- Одна задача — одна ветка — один PR. Ветка живёт не дольше двух дней; долгие ветки
  расходятся с основной и порождают конфликты.
- PR обязан: собираться, проходить тесты и статический анализ, иметь описание что и зачем.
- Минимум одно одобрение. Ревьюер — из пары, владеющей соседним пакетом, а не из своей.
- PR больше ~400 изменённых строк разбивается на части.

### 8.2 Общее определение готовности
Задача считается выполненной, только если выполнены **все** пункты:
- [ ] Код собирается, все тесты зелёные локально и в CI.
- [ ] Написаны тесты на новую логику, включая негативные сценарии.
- [ ] Для эндпоинтов: есть тесты на права и на изоляцию арендатора.
- [ ] Изменения схемы оформлены миграцией; повторный запуск на чистой базе проходит.
- [ ] Новые эндпоинты описаны в OpenAPI и отображаются в документации.
- [ ] Значимые решения зафиксированы в описании PR.
- [ ] Секретов и отладочного вывода в коде нет.
- [ ] PR прошёл ревью и одобрен.

### 8.3 Фиксация решений
Значимые архитектурные решения оформляются короткой записью: контекст, варианты, выбор,
последствия. Хранятся в `docs/adr/`. Цель — чтобы через месяц никто не переспрашивал
«почему так сделано».

### 8.4 Работа десятью разработчиками
- Пара разработчиков владеет пакетом целиком — от контроллера до миграций.
- Контракты между пакетами согласуются **до** начала параллельной работы.
- Общие пакеты (`common`, `security`, `tenant`) стабилизируются в первую неделю и после
  этого меняются только по согласованию — от них зависят все.
