T-036 — Создание заявки клиентом
Назначение
Реализовать клиентский API для создания заявки с проверкой входных данных, привязкой к текущему пользователю и арендатору, а также безопасной обработкой повторных запросов.
Endpoint
`POST /api/v1/client/requests`
Заголовки
`Authorization: Bearer <token>` — действующий токен аутентификации.
`Idempotency-Key: <key>` — обязательный ключ идемпотентности длиной не более 128 символов.
`Content-Type: application/json`.
Тело запроса
```json
{
  "typeId": "00000000-0000-0000-0000-000000000000",
  "subject": "Не работает оборудование",
  "description": "Описание проблемы и необходимые детали",
  "dataParams": {
    "location": "Офис 12",
    "equipmentCode": "EQ-42"
  },
  "priority": "NORMAL",
  "desiredDueAt": "2026-10-20T12:00:00Z"
}
```
Поля:
Поле	Обязательность	Правила
`typeId`	Обязательно	UUID типа заявки. Тип должен существовать, принадлежать текущему арендатору и быть активным.
`subject`	Обязательно	Непустая строка после проверки пробелов, максимум 255 символов.
`description`	Обязательно	Непустая строка после проверки пробелов, максимум 10 000 символов.
`dataParams`	Необязательно	Дополнительные JSON-совместимые параметры; может отсутствовать или быть `null`.
`priority`	Необязательно	`LOW`, `NORMAL`, `HIGH` или `URGENT`. Если не задан, используется приоритет по умолчанию типа заявки; если он не задан, используется `NORMAL`.
`desiredDueAt`	Необязательно	Желаемые дата и время в формате ISO-8601.
Идентификаторы `authorId` и `tenantId` не принимаются как источник авторства или принадлежности заявки. Если клиент передаёт такие поля в дополнительном содержимом запроса, они не должны переопределять данные доверенного серверного контекста.
Правила обработки
Пользователь должен быть аутентифицирован и иметь право `REQUEST_CREATE`.
Автор заявки определяется из контекста текущего пользователя, а арендатор — из контекста текущего арендатора.
Тип заявки проверяется в пределах текущего арендатора. Неизвестный тип или тип другого арендатора приводит к ответу `404 Not Found`; неактивный тип отклоняется как ошибка валидации.
При создании заявке присваивается статус `NEW`.
Сроки ответа и решения рассчитываются серверной логикой назначения дедлайнов.
Поля запроса проходят bean validation. Ошибки валидации возвращаются в стандартном формате ошибок API с указанием проблемных полей.
Идемпотентность
Для каждого запроса обязателен заголовок `Idempotency-Key`.
Область уникальности ключа: текущий арендатор, текущий пользователь и операция создания клиентской заявки.
Повторный запрос с тем же ключом и тем же содержимым возвращает сохранённый первоначальный результат, не создавая новую заявку.
Повторное использование того же ключа с другим содержимым возвращает `409 Conflict` с кодом `IDEMPOTENCY_KEY_REUSED`.
При конкурентных запросах с одинаковым ключом должна быть создана не более чем одна заявка, а повторные вызовы должны получить сохранённый результат.
Результат идемпотентного выполнения сохраняется в базе данных. Таблица записей идемпотентности связана с арендатором и пользователем и защищена ограничением уникальности и политикой изоляции арендаторов.
Успешный ответ
При успешном создании возвращается `201 Created` и тело с данными созданной заявки, включая её идентификатор:
```json
{
  "id": "00000000-0000-0000-0000-000000000001",
  "typeId": "00000000-0000-0000-0000-000000000000",
  "subject": "Не работает оборудование",
  "description": "Описание проблемы и необходимые детали",
  "dataParams": {
    "location": "Офис 12",
    "equipmentCode": "EQ-42"
  },
  "priority": "NORMAL",
  "status": "NEW",
  "desiredDueAt": "2026-10-20T12:00:00Z",
  "createdAt": "2026-10-18T10:30:00Z",
  "firstResponseDueAt": "2026-10-18T14:30:00Z",
  "resolutionDueAt": "2026-10-20T10:30:00Z"
}
```
Значения UUID и даты в примере приведены исключительно для иллюстрации. Фактические значения определяются приложением.
Основные ответы с ошибками
HTTP-статус	Сценарий
`400 Bad Request`	Некорректные поля запроса, превышение ограничений длины или неактивный тип заявки.
`401 Unauthorized`	Запрос не аутентифицирован.
`403 Forbidden`	Пользователь аутентифицирован, но не имеет права `REQUEST_CREATE`.
`404 Not Found`	Тип заявки не существует или недоступен текущему арендатору.
`409 Conflict`	Один `Idempotency-Key` повторно использован с другим содержимым (`IDEMPOTENCY_KEY_REUSED`).
Фактическая структура тела ошибки определяется общим контрактом ошибок приложения.
Хранение и миграция
Flyway-миграция создаёт таблицу записей идемпотентности со следующими данными:
идентификатор записи;
идентификатор арендатора и пользователя;
код операции и ключ идемпотентности;
хеш исходного запроса;
HTTP-статус и сохранённое тело ответа;
время создания и обновления.
Для записи предусмотрены внешние ключи, уникальность сочетания арендатора, пользователя, операции и ключа, а также политика Row-Level Security для изоляции данных арендаторов.
Проверки
Интеграционные тесты покрывают:
успешное создание заявки и ответ `201 Created`;
начальный статус `NEW` и применение приоритета по умолчанию;
игнорирование попыток подменить автора и арендатора;
ошибки валидации;
неизвестный, неактивный и принадлежащий другому арендатору тип заявки;
запрос без аутентификации;
повторный запрос с одинаковым ключом и телом;
повторное использование ключа с другим телом;
конкурентные запросы с одним ключом идемпотентности.
Полная проверка проекта: `./gradlew clean build`.
