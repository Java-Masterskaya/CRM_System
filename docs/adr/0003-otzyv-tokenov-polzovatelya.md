# 0003. Немедленный отзыв токенов пользователя

**Статус:** предложено
**Дата:** 2026-11-01

## Контекст

T-111 требует немедленно закрывать доступ при блокировке пользователя и отзывать все
его токены при снятии роли `ADMIN`. Ожидание истечения JWT не выполняет это требование.
При обычном запросе права берутся из токена; перечитывать роли из БД не требуется.

## Варианты

- Отзывать только refresh-токены: уже выданный access продолжает работать до истечения.
- Хранить каждый отозванный access-токен: требуется отдельный реестр и его очистка.
- Хранить версию доступа пользователя: одно увеличение версии отзывает все его
  предыдущие access-токены без отдельного списка токенов.

## Решение

В реализации T-111 выбран третий вариант. В `users` хранится `access_token_version`,
в JWT — `access_version`. Блокировка и снятие `ADMIN` увеличивают версию и отзывают
refresh-токены в общей транзакции с изменением пользователя и записью идемпотентности.
Разблокировка не уменьшает версию и не восстанавливает старые сессии.

После проверки подписи и срока JWT выполняется один индексированный запрос к состоянию
отзыва. Роли и права при этом не загружаются. Частичный индекс содержит пользователей
с историей отзыва, заблокированных и удалённых. JWT без версии трактуется как версия `0`;
миграция заранее отзывает доступ уже заблокированных и удалённых пользователей.

Вход, обновление токенов и административные изменения сериализуются блокировкой строки
пользователя. Порядок блокировок общий: пользователь, затем refresh-токены. Вход и refresh
получают актуальные статус и версию после ожидания блокировки.

Между модулями используются публичные порты `user.api.UserAccessTokenState` и
`user.api.UserRefreshTokenRevoker`. Реализация отзыва refresh находится в `security`
и требует уже открытую транзакцию. Модуль `user` не зависит от внутренних типов `security`.

## Последствия

Доступ прекращается после фиксации административной транзакции, без ожидания срока JWT.
Уже выполняющийся запрос это решение не прерывает. На каждую аутентификацию JWT добавляется
одно обращение к БД, поэтому её доступность нужна и для проверки access-токенов.
Пользователи с историей отзыва остаются в частичном индексе после разблокировки.

При добавлении новых причин отзыва необходимо использовать ту же версию и транзакцию,
чтобы старые токены не стали действительными повторно. Контракт и тесты описаны в
[API T-111](../API_T111_TENANT_USER_MANAGEMENT.md).
