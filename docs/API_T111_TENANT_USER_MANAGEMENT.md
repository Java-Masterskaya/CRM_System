# T-111 · Управление пользователями арендатора

Контракт API для задачи [#65](https://github.com/Java-Masterskaya/CRM_System/issues/65).
Документ фиксирует контракт административного HTTP API и правила обработки запросов.

## Общие правила

- Базовый путь: `/api/v1/admin/users`.
- Все операции требуют `Authorization: Bearer <access-token>`.
- Арендатор определяется из токена через `TenantContext`. `tenantId` и `tenantSlug`
  не являются параметрами этих операций и не могут менять область доступа.
- Пользователь определяется параметром `{id}` внутри текущего арендатора.
  Неизвестный, удалённый и принадлежащий другому арендатору пользователь дают одинаковый `404`.
- Доступ проверяется по правам для конкретного маршрута и HTTP-метода в `SecurityConfig`,
  а также на методах сервиса. По умолчанию у `OPERATOR` и `CLIENT`
  нет прав на эти операции, поэтому они получают `403`.
- Изменяющие операции принимают JSON и обязательный `Idempotency-Key` длиной от 1 до 128
  символов; ключ из одних пробелов недопустим.
- Ответы и логи не содержат паролей, их хэшей, access- и refresh-токенов.

| Метод и путь | Назначение | Право | Успех |
|---|---|---|---|
| `GET /api/v1/admin/users` | Список с фильтрами | `USER_READ` | `200 OK` |
| `POST /api/v1/admin/users` | Создание оператора или администратора | `USER_MANAGE` | `201 Created` |
| `PATCH /api/v1/admin/users/{id}/status` | Блокировка или разблокировка | `USER_MANAGE` | `200 OK` |
| `PUT /api/v1/admin/users/{id}/roles` | Замена набора назначенных ролей | `USER_MANAGE` | `200 OK` |

`ROLE_MANAGE` предназначено для изменения состава прав самих ролей. Назначение существующих
ролей пользователю проверяется по `USER_MANAGE`, как предусмотрено `docs/permissions.md`.

## Представление пользователя

Создание, изменение статуса и изменение ролей возвращают одно представление:

```json
{
  "id": "00000000-0000-0000-0000-000000000101",
  "email": "operator@example.com",
  "name": "Иван Петров",
  "status": "ACTIVE",
  "roles": ["OPERATOR"]
}
```

`roles` содержит уникальные коды ролей в алфавитном порядке. Статус — `ACTIVE` или `BLOCKED`.
Пароль, `passwordHash` и внутренние сведения об отзыве токенов отсутствуют.
У существующих пользователей без заполненного имени поле `name` может быть `null`.

## Список пользователей

`GET /api/v1/admin/users`

| Параметр | По умолчанию | Правила |
|---|---|---|
| `role` | Без фильтра | Один код роли; пользователь подходит, если у него есть эта роль |
| `status` | Без фильтра | `ACTIVE` или `BLOCKED` |
| `page` | `0` | Номер страницы, начиная с нуля |
| `size` | `20` | От 1 до 100 |
| `sort` | `email,asc` | Поля `email`, `name`, `status`, `id`; направления `asc` и `desc` |

Фильтры `role` и `status` применяются совместно. Неизвестный код роли даёт пустой список.
Пустой `role`, неизвестный статус, недопустимая сортировка или пагинация дают `400`.
Параметр `sort` можно повторять. К сортировке добавляется `id` как стабильный критерий,
если он ещё не указан.

Список содержит только неудалённых пользователей текущего арендатора. Пользователь с несколькими
ролями появляется один раз; `totalElements` также считает пользователей, а не связи с ролями.
Формат страницы соответствует общему `PageResponse`:

```json
{
  "content": [
    {
      "id": "00000000-0000-0000-0000-000000000101",
      "email": "operator@example.com",
      "name": "Иван Петров",
      "status": "ACTIVE",
      "roles": ["OPERATOR"]
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

## Создание пользователя

`POST /api/v1/admin/users`

```json
{
  "email": "operator@example.com",
  "name": "Иван Петров",
  "temporaryPassword": "<временный пароль>",
  "roles": ["OPERATOR"]
}
```

Значение `temporaryPassword` в примере — обозначение, а не готовый пароль.

| Поле | Правила |
|---|---|
| `email` | Обязательный корректный email, не более 255 символов; внешние пробелы убираются |
| `name` | Обязательная непустая строка, не более 255 символов; внешние пробелы убираются |
| `temporaryPassword` | Обязательный пароль, соответствующий действующей `PasswordPolicy` |
| `roles` | Обязательный непустой набор без повторов; при создании допустимы только `OPERATOR` и `ADMIN` |

Временный пароль задаёт администратор и передаёт пользователю вне этого API. Приложение
сохраняет только BCrypt-хэш; пароль не возвращается в ответе. Автоматическая генерация,
доставка пароля и обязательная смена при первом входе этим контрактом не вводятся.
Пользователь может изменить пароль существующей операцией смены пароля.
Нарушения политики пароля возвращаются в `errors` для поля `temporaryPassword`.

Email уникален без учёта регистра среди неудалённых пользователей текущего арендатора.
Совпадение email у другого арендатора не препятствует созданию. Конкурентное создание
с одинаковым email не должно приводить к двум пользователям.

Все назначаемые роли должны существовать у текущего арендатора. Пользователь создаётся
со статусом `ACTIVE`; создание пользователя и назначение ролей выполняются одной транзакцией.
Ответ `201` содержит представление созданного пользователя.

## Изменение статуса

`PATCH /api/v1/admin/users/{id}/status`

```json
{
  "status": "BLOCKED"
}
```

- `status` обязателен; допустимы только `ACTIVE` и `BLOCKED`.
- `BLOCKED` блокирует пользователя и отзывает все его refresh-токены на всех устройствах.
  Уже выданные access-токены перестают приниматься до истечения их срока: защищённые
  запросы с ними возвращают `401`.
- `ACTIVE` разрешает новый вход. Разблокировка не восстанавливает ранее отозванные токены.
- Администратор не может установить себе `BLOCKED`.
- Повторная установка уже действующего статуса возвращает текущее представление с `200`.
- Изменение статуса и запись сведений об отзыве токенов фиксируются атомарно.

## Замена назначенных ролей

`PUT /api/v1/admin/users/{id}/roles`

```json
{
  "roles": ["ADMIN", "CLIENT"]
}
```

- `roles` — обязательный непустой набор уникальных кодов существующих ролей текущего арендатора.
  В отличие от создания, здесь разрешена и роль `CLIENT`, в том числе вместе с `ADMIN`.
- Запрос полностью заменяет назначенный набор ролей. Он не меняет состав прав самих ролей.
- Неизвестные и недоступные текущему арендатору коды ролей отклоняются одинаково как ошибка
  валидации поля `roles`.
- Порядок кодов не влияет на результат. Повторная установка того же набора возвращает `200`.
- Администратор может изменить собственный набор, только если сохраняет роль `ADMIN`.
  Проверка использует фактическое назначение ролей в БД и идентификатор текущего пользователя.
- При снятии `ADMIN` у другого пользователя отзываются все его refresh- и access-токены.
  Новый вход выдаёт права уже по новому набору ролей.
- При других изменениях ролей новые права попадают в токен при следующем входе или обновлении.
  Уже выданный access-токен сохраняет прежние права до истечения срока.
- Замена ролей, проверка ограничений и необходимый отзыв выполняются одной транзакцией;
  параллельные изменения не должны обходить запрет снятия собственной роли `ADMIN`.

## Граница модулей и транзакция отзыва

Административный сервис в модуле `user` вызывает публичный порт
`user.api.UserRefreshTokenRevoker`. Реализация `security.service.impl.UserRefreshTokenRevokerImpl`
делегирует отзыв существующему `RefreshTokenService`. Модуль `user` не импортирует сервисы,
репозитории или сущности `security`.

Порт требует уже открытую транзакцию (`Propagation.MANDATORY`). Он не открывает отдельную
транзакцию и не переносит отзыв на обработчик после фиксации. Изменение статуса или ролей,
увеличение версии доступа, отзыв refresh-токенов и результат идемпотентности фиксируются
либо откатываются вместе. Вызов порта без транзакции отклоняется до изменения токенов.
Принадлежность целевого пользователя арендатору проверяется до вызова порта.

Обратное чтение состояния JWT также идёт через публичный API — `user.api.UserAccessTokenState`.
Его реализация остаётся в `user`. Между модулями не передаются JPA-сущности или репозитории.

## Отзыв access-токенов

Выбор механизма и его последствия зафиксированы в
[ADR 0003](adr/0003-otzyv-tokenov-polzovatelya.md).

Пользователь хранит монотонную `access_token_version`, а access-токен содержит claim
`access_version`. Блокировка и снятие `ADMIN` увеличивают версию в той же транзакции,
что и изменение пользователя и отзыв refresh-токенов. Разблокировка не уменьшает версию.
Новый вход или refresh получают текущую версию и права после блокировки строки пользователя.
Общий порядок блокировок: пользователь, затем refresh-токены.

При аутентификации предъявленного JWT выполняется один запрос к состоянию отзыва,
без чтения ролей и прав. Частичный индекс `idx_users_access_revocations` содержит
заблокированных, удалённых пользователей и пользователей с историей отзыва.

Токены без `access_version`, выданные до обновления, считаются токенами версии `0`.
Они принимаются только пока доступ пользователя не отозван. Миграция назначает ненулевую
версию уже заблокированным и удалённым пользователям, чтобы разблокировка не оживила их
старые токены, и отзывает их существующие refresh-токены. Отрицательная, дробная или строковая
версия отклоняется как недействительный JWT.

## Изменение схемы БД

Изменения поставляются новой миграцией
`V202610281800__user_access_token_revocation.sql`. Она добавляет в `users` поле
`access_token_version`: `BIGINT NOT NULL DEFAULT 0` с запретом отрицательных значений,
и частичный индекс проверки отзыва.

Для существующих заблокированных и удалённых пользователей всех арендаторов версия
устанавливается в `1`, а существующие refresh-токены отзываются. Действующие сессии активных
пользователей сохраняются. Повторный запуск Flyway не выполняет уже применённую миграцию.
Таблицы пользователей, ролей и связей используются существующие; новых таблиц T-111 не создаёт.

## Идемпотентность

Для `POST`, `PATCH` и `PUT` применяются общие правила из SPEC §5.2:

- Область ключа: текущий арендатор, текущий пользователь и конкретная операция.
  Идентификатор целевого пользователя учитывается при определении запроса.
- Повтор того же запроса с тем же ключом возвращает сохранённые HTTP-статус и представление,
  не создаёт пользователя повторно и не повторяет отзыв токенов.
- Тот же ключ с другим запросом даёт `409 IDEMPOTENCY_KEY_REUSED`.
- При сравнении запросов набор ролей нормализуется: перестановка тех же кодов не считается
  изменением содержимого.
- Проверки текущей аутентификации и прав выполняются и для повторных запросов.
- Открытый пароль и исходное тело запроса с паролем не сохраняются в записи идемпотентности.

## Ошибки

Ошибки возвращаются как `application/problem+json` через общий механизм Problem Details.
Ответ содержит `code`, `requestId` и стандартные поля; ошибки валидации дополнительно
содержат `errors`. Идентификатор запроса передаётся также в `X-Request-Id`.

| HTTP | Код | Причина |
|---|---|---|
| `400` | `VALIDATION_FAILED` | Некорректные поля, роли, пароль, параметры списка или ключ идемпотентности |
| `401` | `UNAUTHENTICATED` | Нет действующей аутентификации; токен недействителен или отозван |
| `403` | `ACCESS_DENIED` | Нет права на операцию |
| `404` | `NOT_FOUND` | Целевой пользователь не существует, удалён или принадлежит другому арендатору |
| `409` | `ALREADY_EXISTS` | Email уже занят внутри арендатора |
| `409` | `USER_SELF_BLOCK_FORBIDDEN` | Попытка заблокировать самого себя |
| `409` | `USER_SELF_ADMIN_ROLE_REMOVAL_FORBIDDEN` | Попытка снять с себя роль `ADMIN` |
| `409` | `IDEMPOTENCY_KEY_REUSED` | Ключ повторно использован с другим запросом |

Коды `USER_SELF_BLOCK_FORBIDDEN` и `USER_SELF_ADMIN_ROLE_REMOVAL_FORBIDDEN` добавлены
в общий каталог ошибок. Проверка прав выполняется до поиска
целевого пользователя, поэтому отсутствие права не позволяет выяснить существование чужой записи.

## Проверка реализации

Интеграционные тесты наследуются от `BaseIntegrationTest` и используют PostgreSQL
через Testcontainers. HTTP-сценарии административного API выполняются при включённой
обязательной авторизации и получают настоящие токены через `/auth/login`.

| Требование | Проверки |
|---|---|
| Создание оператора и администратора, вход и доступ по выданным правам | `AdminUserCreationServiceIntegrationTest`, `AdminUserControllerIntegrationTest` |
| Список, фильтры, пагинация, отсутствие чужих и удалённых пользователей | `AdminUserQueryServiceIntegrationTest`, `AdminUserControllerIntegrationTest` |
| Отказ оператору, клиенту и пользователю без нужного права | Тесты контроллера и сервисов создания, чтения и изменения пользователей |
| Немедленный отзыв access и всех refresh при блокировке и снятии ADMIN | `AdminUserManagementServiceIntegrationTest`, `AdminUserControllerIntegrationTest` |
| Защита от самоблокировки и снятия собственной ADMIN, конкурентные изменения | `AdminUserManagementServiceIntegrationTest` |
| Идемпотентность, конфликты ключей, отсутствие частичных изменений при откате | Тесты сервисов создания и изменения, тесты контроллера |
| Обновление существующей БД и миграция на чистой БД | `UserAccessTokenMigrationIntegrationTest` |
| Общая транзакция отзыва refresh и границы модулей | `UserRefreshTokenRevokerIntegrationTest`, `ArchitectureRulesTest` |

Полная проверка проекта (при работающем Docker):

```bash
./gradlew check --continue
```

Она включает `test`, `itTest`, Checkstyle, SpotBugs и порог покрытия JaCoCo.
Результаты доступны в `build/reports`; `--continue` позволяет получить результаты
независимых проверок, даже если одна из них завершается ошибкой.
