# Начальные роли и права (T-021)

Права хранятся в `permissions`, а роли — в `roles`. В БД код права хранится строкой;
допустимые коды перечислены в `PermissionCode`, поэтому проверка права в Java принимает enum,
а не произвольную строку.

Миграция `V202610011900__seed_default_roles_and_permissions.sql` наполняет существующих
арендаторов. При создании нового арендатора `TenantService` явно вызывает
`TenantAccessSeeder` в той же транзакции. Функция `seed_tenant_access_defaults` остаётся
идемпотентной для повторного наполнения и восстановления данных; автоматического триггера
на `tenants` больше нет.

## Права и операции

| Право | Операция |
|---|---|
| `REQUEST_CREATE` | Создать заявку |
| `REQUEST_READ_OWN` | Читать собственные заявки и карточки |
| `REQUEST_READ_ALL` | Читать заявки в административном контуре арендатора |
| `REQUEST_CANCEL_OWN` | Отменить собственную заявку, если переход допустим |
| `REQUEST_STATUS_CHANGE` | Перевести заявку в допустимый статус |
| `REQUEST_ASSIGN` | Назначить, снять или переназначить исполнителя |
| `REQUEST_EDIT` | Изменить операционные поля заявки |
| `REQUEST_AUDIT_READ` | Читать журнал аудита с учётом доступной области заявок |
| `COMMENT_PUBLIC_CREATE_OWN` | Добавить публичный комментарий к собственной заявке |
| `COMMENT_PUBLIC_CREATE` | Добавить публичный комментарий оператором |
| `COMMENT_INTERNAL_CREATE` | Добавить внутренний комментарий |
| `ATTACHMENT_CREATE_OWN` | Приложить файл к собственной заявке |
| `ATTACHMENT_READ_OWN` | Читать вложения собственной заявки |
| `ATTACHMENT_MANAGE` | Управлять вложениями в административном контуре |
| `PROFILE_READ_OWN` | Читать собственный профиль |
| `PROFILE_EDIT_OWN` | Изменить собственные данные и пароль |
| `USER_READ` | Читать пользователей арендатора |
| `USER_MANAGE` | Создавать и блокировать пользователей, назначать им роли |
| `ROLE_MANAGE` | Управлять составом ролей арендатора |
| `TENANT_SETTINGS_READ` | Читать настройки арендатора |
| `TENANT_SETTINGS_MANAGE` | Изменять настройки арендатора |
| `REQUEST_TYPE_MANAGE` | Управлять типами заявок |
| `SLA_POLICY_MANAGE` | Управлять SLA-политиками и рабочим календарём |
| `INTEGRATION_MANAGE` | Управлять интеграциями арендатора |
| `ANALYTICS_READ` | Просматривать аналитику арендатора |

## Состав ролей

| Раздел | `CLIENT` | `OPERATOR` | `ADMIN` |
|---|---|---|---|
| Заявки | `REQUEST_CREATE`, `REQUEST_READ_OWN`, `REQUEST_CANCEL_OWN` | `REQUEST_READ_ALL`, `REQUEST_STATUS_CHANGE`, `REQUEST_ASSIGN`, `REQUEST_EDIT`, `REQUEST_AUDIT_READ` | Права оператора |
| Комментарии | `COMMENT_PUBLIC_CREATE_OWN` | `COMMENT_PUBLIC_CREATE`, `COMMENT_INTERNAL_CREATE` | Права оператора |
| Вложения | `ATTACHMENT_CREATE_OWN`, `ATTACHMENT_READ_OWN` | `ATTACHMENT_MANAGE` | `ATTACHMENT_MANAGE` |
| Профиль | `PROFILE_READ_OWN`, `PROFILE_EDIT_OWN` | `PROFILE_READ_OWN`, `PROFILE_EDIT_OWN` | `PROFILE_READ_OWN`, `PROFILE_EDIT_OWN` |
| Пользователи и роли | — | — | `USER_READ`, `USER_MANAGE`, `ROLE_MANAGE` |
| Настройки и справочники | — | — | `TENANT_SETTINGS_READ`, `TENANT_SETTINGS_MANAGE`, `REQUEST_TYPE_MANAGE`, `SLA_POLICY_MANAGE`, `INTEGRATION_MANAGE` |
| Аналитика | — | — | `ANALYTICS_READ` |

`ADMIN` включает административные права `OPERATOR`, но не клиентские права. Это намеренно:
ТЗ §3.1 описывает ADMIN как оператора с дополнительными полномочиями, а SPEC §5.1 разделяет
клиентский и административный контуры. Если администратору нужно выполнять клиентские операции,
ему можно назначить дополнительную роль `CLIENT` того же арендатора; пользователь может иметь
несколько ролей.

Право `REQUEST_READ_OWN` не заменяет проверку владельца заявки. Владение записью и область
доступа проверяются в бизнес-логике отдельно от наличия права. Все операции также ограничены
текущим арендатором. `CLIENT` не получает прав на чтение всех заявок, смену их статуса или
управление пользователями. `OPERATOR` не получает прав управления пользователями и настройками
арендатора.

Коды сопоставлены с операциями и ролями в ТЗ: роли — раздел 3.1, клиентские операции — 6.2,
административные — 6.3, SLA — 6.4, вложения — 6.6, аудит — 6.7, аналитика — 6.8,
интеграции — 6.9. `ANALYTICS_READ` и `INTEGRATION_MANAGE` соответствуют возможностям *Could*.

Назначения пользователей и прав хранят `tenant_id`. Миграция
`V202610021000__harden_tenant_access_defaults.sql` добавляет составные внешние ключи в
`user_roles` и `role_permissions`; БД отклоняет назначения между разными арендаторами, а старые
сиротские или кросс-арендаторские строки удаляются. Запрос выдачи прав дополнительно сопоставляет
арендатора на каждом соединении.

Исходная миграция создания ролей и прав не редактируется после применения: последующие изменения
схемы поставляются отдельными миграциями.

Синтетический арендатор `System` с нулевым UUID создавался ранней миграцией только как
заполнитель. Новая миграция деактивирует его и удаляет принадлежащие ему роли и права; функция
наполнения игнорирует этот UUID.

Часть операций ещё не реализована в коде. Для них права являются начальными записями каталога,
а проверки должны быть подключены вместе с соответствующими API. Ниже не задана отдельная
гранулярность чтения комментариев или вложений: доступ к ним следует из права чтения заявки
и обязательной проверки владения/области доступа.
