# Валидация входных данных — памятка

Как проверять данные на входе в API, чтобы ошибки у всех пар выглядели одинаково.
Формат ошибок — из T-005 (#6), реализация валидации — T-006 (#7).

## Что происходит при ошибке

| Ситуация | Статус | `code` | Где указано поле |
|---|---|---|---|
| Поле тела не прошло проверку (`@Valid @RequestBody`) | 400 | `VALIDATION_FAILED` | `errors[].pointer`, например `#/subject` |
| Параметр не прошёл проверку (`@RequestParam @Min(1)`) | 400 | `VALIDATION_FAILED` | `errors[].parameter`, например `size` |
| Параметр неверного типа (`?page=abc`) | 400 | `VALIDATION_FAILED` | `errors[].parameter` |
| Обязательный параметр не передан | 400 | `VALIDATION_FAILED` | `errors[].parameter` |
| Тело не разбирается как JSON | 400 | `MALFORMED_REQUEST` | — |
| Тело больше лимита | 413 | `PAYLOAD_TOO_LARGE` | — |

Все ошибки одного запроса приходят **в одном ответе** — клиенту не нужно исправлять поля по одному.

## Тело запроса

DTO — это `record`, ограничения ставятся на компоненты, в контроллере — `@Valid`:

```java
public record CreateItemRequest(
        @NotBlank @Size(max = 255) String name,
        @Size(max = 2000) String comment,
        @NotNull @Positive Integer quantity) {
}
```

```java
@PostMapping("/client/items")
public ResponseEntity<ItemResponse> create(@Valid @RequestBody CreateItemRequest request) {
    ...
}
```

Имена в примерах условные. Путь пишется **без** `/api/v1` — префикс добавляет `context-path`.

## Параметры запроса

Ограничения ставятся прямо на параметр метода:

```java
@GetMapping("/admin/items/{id}")
public ItemResponse get(@PathVariable @Positive Long id) {
    ...
}
```

**Не ставьте `@Validated` на класс контроллера.** Spring 6.1 проверяет ограничения на параметрах
сам, но только если класс **не** помечен `@Validated` — иначе включается другой механизм,
и ошибка не попадёт в общий формат.

Для списков параметры `page`, `size`, `sort` проверять вручную не нужно — это делает
`PageRequests.toPageable` из T-007 (#8).

## Длина текстовых полей

- `@Size(max = N)`, где **N равно длине колонки** в миграции: `VARCHAR(255)` → `@Size(max = 255)`.
  Иначе база отклонит запись уже после проверки, и клиент получит 500 вместо понятной ошибки.
- Для колонок `TEXT` без длины всё равно ставьте разумный `@Size(max = ...)`: без него длину
  ограничивает только общий лимит тела.

## Какую аннотацию выбрать для строки

| Аннотация | `null` | `""` | `"   "` |
|---|---|---|---|
| `@NotNull` | ошибка | проходит | проходит |
| `@NotEmpty` | ошибка | ошибка | проходит |
| `@NotBlank` | ошибка | ошибка | ошибка |

Для обязательного текста почти всегда нужен `@NotBlank`.

## Тексты сообщений

- Русские тексты стандартных аннотаций лежат в `src/main/resources/ValidationMessages.properties`.
  Они одинаковые на любой машине и не зависят от языка системы.
- Если нужен свой текст — атрибут `message`: `@Size(max = 255, message = "не длиннее 255 символов")`.
- В сообщение не пишите технические детали: имена таблиц, классов, регулярные выражения.

## Лимит размера тела

Настраивается свойством `app.web.max-request-body-size`, по умолчанию `1MB`. Запрос с большим
`Content-Length` отклоняется сразу, не доходя до контроллера. Если длина заранее не указана,
чтение прерывается, как только данных становится больше лимита.

## Как тестировать

Используйте `@WebMvcTest`: он поднимает только веб-слой, базе данных и Docker запуск не нужен.
Образец — `src/test/java/ru/practicum/crm/common/error/RequestValidationTest.java`.

Минимальный набор для эндпоинта, который принимает данные:

- пустое значение обязательного поля;
- превышение длины;
- неверный формат (например, email или число);
- несколько ошибок в одном запросе.
