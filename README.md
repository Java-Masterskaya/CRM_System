# CRM_System

Многоарендная CRM-система приёма и ведения заявок на обработку данных.
Клиент подаёт заявку — оператор ведёт её по процессу до выполнения. Система следит
за сроками, распределяет нагрузку между операторами и уведомляет участников.

**Стек:** Java 21 · Spring Boot 3 · Gradle · PostgreSQL

## Правила, которые нельзя нарушать

1. **Идентификатор арендатора берётся только из токена.** Никогда из тела, пути или
   параметров запроса. Одна ошибка здесь — утечка данных между компаниями.
2. **Запрет по умолчанию.** Всё, что не разрешено явно, закрыто.
3. **Чужая сущность не существует.** Обращение к недоступному объекту возвращает
   «не найдено», а не «запрещено».
4. **Схема БД — только миграциями.** Автогенерация схемы запрещена.
5. **Одна задача — одна ветка — один PR.** Ветка живёт не дольше двух дней.
6. **Секретов в репозитории нет.** Все чувствительные значения — из окружения.

Полное определение готовности задачи — в [SPEC, раздел 8.2](docs/SPEC.md).

## Локальное окружение (Docker Compose)

Проект запускается вместе со всеми необходимыми сервисами — PostgreSQL 16 и почтовой заглушкой MailHog — с помощью Docker Compose.

### Подготовка

Перед первым запуском скопируйте файл с примером переменных окружения:

```bash
cp .env.example .env
```

Затем откройте `.env` и **обязательно заполните `POSTGRES_PASSWORD`**.

Например:

```env
POSTGRES_PASSWORD=local_password
```

`POSTGRES_DB` и `POSTGRES_USER` можно оставить пустыми: Docker Compose использует значения по умолчанию:

* `POSTGRES_DB=crm_db`
* `POSTGRES_USER=crm_user`

После заполнения пароля запустите окружение:

```bash
docker compose up
```

Пустой `POSTGRES_PASSWORD` не допускается. Если значение не задано, PostgreSQL не запустится.

Профили Spring:

* `local` — профиль по умолчанию для разработки;
* `test` — профиль для автотестов;
* `prod` — профиль для запуска с внешними сервисами.

`local` используется для разработки и запускается вместе с локальными PostgreSQL и MailHog.

`test` используется для автотестов. Пароль тестовой базы имеет значение по умолчанию и не требует GitHub Secret.

`prod` предназначен для запуска с внешними сервисами и требует полного набора обязательных переменных окружения.

Чувствительные значения, включая пароли базы данных и SMTP, не хранятся
в конфигурационных файлах и передаются через переменные окружения.

Обязательные настройки валидируются при старте приложения. При отсутствии
необходимого значения запуск завершается с ошибкой, содержащей имя недостающей
настройки.

## Эндпоинты API

Базовый префикс всех эндпоинтов:

```text
/api/v1
```

Служебный эндпоинт проверки работоспособности:

```text
GET http://localhost:8080/api/v1/health
```

 **Важно:** `/api/v1/health` — legacy-эндпоинт из T-001, оставлен для
обратной совместимости. Для проб и healthcheck'ов используйте actuator:
`GET /actuator/health/liveness` и `GET /actuator/health/readiness`
на management-порту (см. раздел «Мониторинг и метрики»).

### Документация API (OpenAPI)

Описание API генерируется из кода библиотекой springdoc-openapi. Файлы описания руками
не пишутся и не правятся.

После запуска приложения в среде разработки:

- страница документации: http://localhost:8080/api/v1/swagger-ui.html
- машиночитаемое описание (JSON): http://localhost:8080/api/v1/v3/api-docs

В профиле `prod` обе страницы отключены.

**Для задачи со Spring Security:** при запрете по умолчанию пути документации нужно явно
открыть (`permitAll`) во всех профилях, кроме `prod`: `/v3/api-docs/**`, `/swagger-ui/**`
и `/swagger-ui.html`. Указывайте их **без** префикса `/api/v1` — правила Spring Security
сравнивают путь без `context-path`.

#### Как добавить эндпоинт в документацию

Отдельно ничего делать не нужно: метод контроллера с `@GetMapping`, `@PostMapping` и
другими аннотациями маршрутов попадает в описание автоматически. Схемы запросов и
ответов строятся по классам DTO, поэтому:

- делайте публичные DTO простыми, лучше всего — `record`;
- не используйте Lombok на публичных DTO — по SPEC генерируемые API-модели должны быть
  читаемыми;
- при необходимости добавьте пояснения: `@Operation` — к методу контроллера,
  `@Schema` — к DTO и его полям.

Проверка входит в сборку: тесты в `platform/config` запрашивают `/v3/api-docs` и падают,
если описание не собралось или эндпоинт в него не попал.

## Тестирование проекта

### Соглашение по именованию и качеству тестов

#### Соглашение по именованию (Бизнес-ориентированность)
Имя тестового метода должно описывать **конкретный бизнес-сценарий и ожидаемый результат**, а не просто повторять техническое имя функции в коде.

В проекте допускаются два стиля написания (для сохранения обратной совместимости с параллельными ветками разработки):
1. **Компактный стиль с разделением по фазам:** `[Условие/Сценарий]_[ОжидаемыйРезультат]` через нижнее подчеркивание.  
   *Пример:* `void invalidEmail_throwsException()` или `void customerNotFound_returns404()`
2. **Классический CamelCase-стиль:** Начинающийся с префикса `should...`.  
   *Пример:* `void shouldThrowExceptionWhenEmailIsInvalid()`

#### Золотое правило: Тест обязан уметь падать!
Написание теста считается завершенным только после его **проверки на временную поломку кода (фальсифицируемость)**:
1. Напишите тест и убедитесь, что он проходит успешно (зелёный).
2. Перейдите в тестируемый компонент бизнес-логики и **временно внесите дефект** (закомментируйте валидацию, измените возвращаемый статус, удалите вызов сохранения в БД).
3. Запустите тест снова. Он **обязан упасть по осмысленной причине** с понятным текстом в `AssertionError`. Если тест остался зелёным при сломанном коде — перепишите проверки (`assertions`).
4. Верните код в исходное рабочее состояние.

### Миграции базы данных
## Миграции базы данных

Схема базы данных управляется только через миграции Flyway. Автоматическое создание или изменение таблиц средствами Hibernate запрещено.

Для Hibernate используется режим `ddl-auto: validate`: при запуске приложения схема только проверяется на соответствие ожидаемой.

### Именование миграций

Миграции именуются по времени их создания:

```text
VYYYYMMDDHHMM__description.sql
```

Например:

```text
V202609151501__create_base_schema.sql
```

Для миграций не используется сквозная нумерация (`V1`, `V2`, `V3` и т. д.), чтобы избежать конфликтов при параллельной разработке.

### Неизменяемость и порядок миграций

Миграция считается **введённой в проект**, когда её файл попал в `main`. Это не означает, что она уже применена ко всем существующим базам данных.

При параллельной разработке миграция с более ранним timestamp может попасть в `main` позже миграции с более поздним timestamp. Поэтому включён режим `spring.flyway.out-of-order: true`: если такая миграция ещё не применена конкретной БД, Flyway применит её при следующем запуске, даже если более поздние миграции уже были применены.

Например:

```text
main содержит:

V202609151501__create_base_schema.sql
V202609151400__add_something.sql
```

Если БД уже успела применить `V202609151501`, то при следующем запуске
`V202609151400` будет применена как `out-of-order`.

**Важно:** после попадания миграции в `main` её файл нельзя изменять или удалять. Если требуется изменить уже введённую схему, создаётся новая миграция с новым timestamp.

## Мониторинг и метрики

Для служебного мониторинга используется Spring Boot Actuator + Micrometer.

Служебные endpoints работают на отдельном management-порту `8081` и не входят
в публичный API-префикс `/api/v1`.

### Health checks

Actuator отдаёт два вида ответа: **группы** и **агрегат**. У них разное
назначение, и путать их нельзя.

#### Группы — для проб и автоматики

Используйте **только эти два эндпоинта** во всех healthcheck'ах: LB,
Kubernetes probe, Docker Compose `healthcheck`, системы мониторинга.

Проверка живости:

```text
GET http://localhost:8081/actuator/health/liveness
```

Проверка готовности:

```text
GET http://localhost:8081/actuator/health/readiness
```

`liveness` проверяет состояние самого приложения и не зависит от доступности
внешних систем.

`readiness` дополнительно учитывает доступность базы данных. Поэтому при
недоступной БД:

* `liveness` продолжает успешно проходить;
* `readiness` возвращает состояние `DOWN`.

После восстановления БД `readiness` снова становится `UP` без перезапуска
приложения.

#### Агрегат — только для диагностики

```text
GET http://localhost:8081/actuator/health
```

Агрегат включает **все** health-индикаторы, зарегистрированные в контексте,
в том числе `diskSpace` и `mail`. Его состояние может отличаться от групп:
например, при недоступном SMTP агрегат отдаст `DOWN`, хотя приложение живо
и готово принимать трафик.

**Не используйте агрегат для LB, Kubernetes probe, Docker Compose
`healthcheck` и других автоматических проверок.** Он предназначен для
ручной диагностики при разборе инцидентов: дёрнуть curl'ом и посмотреть,
какой именно компонент упал.

#### Что входит в проверки

| Компонент        | liveness | readiness | aggregate |
| ---------------- | -------- | --------- | --------- |
| `livenessState`  | да       | да        | да        |
| `readinessState` | нет      | да        | да        |
| `db`             | нет      | да        | да        |
| `diskSpace`      | нет      | нет       | да        |
| `mail`           | нет      | нет       | да        |

`mail` намеренно исключён из групп: недоступность SMTP не делает сервис
неготовым принимать трафик. Заявки создаются и обрабатываются, письма
копятся в очереди или логируются. Если SMTP недоступен, это видно в
агрегате — но пробы и LB не страдают.

### Валидация групп

`readiness` включает `db`, а `management.endpoint.health.validate-group-membership`
включён по умолчанию. Поэтому приложение не стартует без DataSource — это осознанное
решение: CRM без БД работать не может, лучше упасть на старте, чем отдавать неверный

### Технические метрики

Метрики доступны через Prometheus endpoint:

```text
GET http://localhost:8081/actuator/prometheus
```

Spring Boot автоматически собирает технические метрики приложения через
Micrometer.

В частности, доступны метрики:

* HTTP-запросов — количество, длительность и статусы/ошибки;
* JVM и процесса приложения;
* пула соединений HikariCP;
* datasource.

Отдельно реализовывать счётчики HTTP-запросов в контроллерах не требуется.

### Продуктовые метрики

Для бизнес-метрик проекта используется Micrometer и Spring-managed `MeterRegistry`.

`CrmMetrics` содержит пример добавления продуктовых метрик для остальных пар.

#### Метрики, используемые в проекте

| Метрика                         | Тип         | Назначение                                                        |
| ------------------------------- | ----------- | ----------------------------------------------------------------- |
| `crm.clients.created`           | `Counter`   | Количество созданных клиентов                                     |
| `crm.operation.duration`        | `Timer`     | Длительность выполнения бизнес-операций                           |
| `crm.outbox.delivery.attempts`  | `Counter`   | Попытки доставки исходящих событий по типу события, исходу и причине |
| `crm.outbox.events`             | `Gauge`     | Исходящие события в состояниях `NEW`, `IN_PROGRESS`, `FAILED`     |
| `crm.outbox.oldest.pending.age` | `TimeGauge` | Сколько ждёт самое давнее недоставленное событие, в секундах      |

#### Очередь исходящих событий

Метрики очереди (T-073) в формате Prometheus:

```text
crm_outbox_delivery_attempts_total{event_type="EMAIL_NOTIFICATION",outcome="retry",reason="MAIL_SERVER_UNAVAILABLE"}
crm_outbox_events{status="NEW"}
crm_outbox_oldest_pending_age_seconds
```

* `outcome` — исход попытки: `success`, `retry` (событие вернулось в очередь) или `failed`
  (попытки исчерпаны); `reason` — код причины неудачи, у успешных попыток — `none`.
* Число событий и возраст считаются по всей очереди при каждом запросе метрик. Доставленные
  (`SENT`) не считаются: до очистки очереди их число растёт без предела, а сколько доставлено,
  видно по счётчику с `outcome="success"`.
* Почтовый сервер недоступен — растут `crm_outbox_delivery_attempts_total` с `outcome="retry"`
  и `crm_outbox_oldest_pending_age_seconds`. После восстановления очередь разбирается, число
  событий `NEW` и возраст возвращаются к нулю.
* Окончательный неуспех пишется в лог с полями `eventId`, `eventType`, `attempts`, `errorCode`.

#### Counter

`Counter` используется, когда нужно считать количество произошедших событий.

Например:

```java
Counter clientsCreated = Counter.builder("crm.clients.created")
        .description("Количество созданных клиентов")
        .register(registry);
clientsCreated.increment();
```

Каждый вызов `increment()` увеличивает значение счётчика на единицу.

В проекте:

```java
metrics.clientCreated();
```

увеличивает:

```text
crm.clients.created
```

Если метод был вызван 10 раз, счётчик содержит значение `10`.

Используйте `Counter` для событий, которые только увеличивают своё количество:

* создан клиент;
* завершена заявка;
* отправлено уведомление;
* выполнена операция.

#### Timer

`Timer` используется для измерения длительности операций.

В проекте используется:

```text
crm.operation.duration
```

Метрика дополнительно разделяется тегами:

```text
operation
outcome
```

Например:

```text
operation=client.create
outcome=success
```

или:

```text
operation=client.create
outcome=error
```

Использование в коде:

```java
var result = metrics.timed(
        "client.create",
        () -> clientService.create(dto)
);
```

`Timer` автоматически измеряет время выполнения `action`.

При успешном завершении используется:

```text
outcome=success
```

При `RuntimeException` и `Error`:

```text
outcome=error
```

Метрика экспортируется с `publishPercentileHistogram()`. Квантили (p50, p95, p99)
рассчитываются на стороне Prometheus через `histogram_quantile()`, а не клиентом.
Это позволяет агрегировать метрики между инстансами приложения.

Таким образом, можно отдельно анализировать длительность успешных и ошибочных
операций.

### Теги

Теги используются для ограниченного набора измерений метрики.

Допустимые примеры:

```text
outcome=success|error
type=individual|company
status=success|error
channel=email|sms
```

Не следует использовать в качестве тегов уникальные идентификаторы:

```text
clientId=...
userId=...
requestId=...
orderId=...
```

Высокая кардинальность тегов увеличивает нагрузку на систему мониторинга.

### Требования к продуктовым метрикам

При добавлении новой продуктовой метрики:

1. Используйте существующий `MeterRegistry`.
2. Выберите подходящий тип метрики (`Counter`, `Timer`, `Gauge`,
   `DistributionSummary`).
3. Используйте имя формата `crm.<module>.<metric>`.
4. Укажите понятное `description`.
5. Используйте только низкокардинальные теги.
6. Не создавайте отдельный Actuator endpoint для своей метрики.
7. Проверьте метрику через:

```text
http://localhost:8081/actuator/prometheus
```
## Логирование

Логи пишутся в stdout в формате JSON, одна запись на строку. Формат задаётся в
`src/main/resources/logback-spring.xml` (`logstash-logback-encoder`).

```json
{"@timestamp":"2026-09-21T15:42:06.593+03:00","message":"Заявка создана","logger_name":"ru.practicum.crm.request.service.RequestService","thread_name":"http-nio-8080-exec-1","level":"INFO","requestId":"7d1f5c0e-3b7a-4a8e-9c2d-0f6b1e2a3c4d"}
```

Кроме стандартных полей в запись попадают значения MDC и структурные аргументы
`kv("ключ", значение)` из `net.logstash.logback.argument.StructuredArguments`.

### Идентификатор запроса

`RequestIdFilter` берёт `X-Request-Id` из запроса, если он состоит из латинских
букв, цифр, `.`, `_`, `-` и не длиннее 64 символов; иначе генерирует UUID.
Идентификатор:

* кладётся в MDC — поле `requestId` есть во всех записях этого запроса;
* возвращается в заголовке `X-Request-Id` каждого ответа и в поле `requestId`
  тела ошибки;
* удаляется из MDC в `finally`, чтобы не утечь в следующий запрос на том же потоке.

### Маскирование чувствительных данных

Настроено в `logback-spring.xml` через `MaskingJsonGeneratorDecorator`:

* значения полей `password`, `newPassword`, `oldPassword`, `token`, `accessToken`,
  `refreshToken`, `authorization`, `secret`, `apiKey`, `email`, `phone` заменяются
  на `****` на любой глубине записи;
* в тексте любого поля `Bearer …` и `Basic …` заменяются на `****`.

Новое чувствительное поле добавьте в `<paths>` и покройте случаем в
`StructuredLoggingTest`. Маскирование — страховка, а не разрешение: пароли,
токены, тела запросов и персональные данные в логи не пишем.

## Mail в тестовом профиле

В тестах mail health check отключён через
`@TestPropertySource(properties = "management.health.mail.enabled=false")`,
потому что тестовое окружение не поднимает SMTP-сервер. Это не меняет
production-контракт: в `local` и `prod` mail входит в агрегат `/actuator/health`,
но не в группы `liveness`/`readiness`.
