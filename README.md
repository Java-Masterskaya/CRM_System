# CRM_System

Многоарендная CRM-система приёма и ведения заявок на обработку данных.
Клиент подаёт заявку — оператор ведёт её по процессу до выполнения. Система следит
за сроками, распределяет нагрузку между операторами и уведомляет участников.

**Стек:** Java 21 · Spring Boot 3 · Gradle · PostgreSQL

## Правила, которые нельзя нарушать

1. **Идентификатор арендатора берётся только из токена.** Никогда из тела, пути или
   параметров запроса. Одна ошибка здесь — утечка данных между компаниями.
2. **Запрет по умолчанию.** Всё, что не разрешено явно, закрыто.
3. **Чужая сущность не существует.** Обращение к недоступному объекту возвращает
   «не найдено», а не «запрещено».
4. **Схема БД — только миграциями.** Автогенерация схемы запрещена.
5. **Одна задача — одна ветка — один PR.** Ветка живёт не дольше двух дней.
6. **Секретов в репозитории нет.** Все чувствительные значения — из окружения.

Полное определение готовности задачи — в [SPEC, раздел 8.2](docs/SPEC.md).

## Локальное окружение (Docker Compose)

Проект запускается вместе со всеми необходимыми сервисами — PostgreSQL 16 и почтовой заглушкой MailHog — с помощью Docker Compose.

### Подготовка

Перед первым запуском скопируйте файл с примером переменных окружения:

```bash
cp .env.example .env
```

Затем откройте `.env` и **обязательно заполните `POSTGRES_PASSWORD`**.

Например:

```env
POSTGRES_PASSWORD=local_password
```

`POSTGRES_DB` и `POSTGRES_USER` можно оставить пустыми: Docker Compose использует значения по умолчанию:

* `POSTGRES_DB=crm_db`
* `POSTGRES_USER=crm_user`

После заполнения пароля запустите окружение:

```bash
docker compose up
```

Пустой `POSTGRES_PASSWORD` не допускается. Если значение не задано, PostgreSQL не запустится.

Профили Spring:

* `local` — профиль по умолчанию для разработки;
* `test` — профиль для автотестов;
* `prod` — профиль для запуска с внешними сервисами.

`local` используется для разработки и запускается вместе с локальными PostgreSQL и MailHog.

`test` используется для автотестов. Пароль тестовой базы имеет значение по умолчанию и не требует GitHub Secret.

`prod` предназначен для запуска с внешними сервисами и требует полного набора обязательных переменных окружения.

Чувствительные значения, включая пароли базы данных и SMTP, не хранятся
в конфигурационных файлах и передаются через переменные окружения.

Обязательные настройки валидируются при старте приложения. При отсутствии
необходимого значения запуск завершается с ошибкой, содержащей имя недостающей
настройки.

### Переменные окружения

| Переменная                   | Обязательно     | Назначение                                                                     |
| ---------------------------- | --------------- | ------------------------------------------------------------------------------ |
| `POSTGRES_DB`                | Нет             | Имя базы PostgreSQL для локального Docker Compose. По умолчанию `crm_db`       |

| `SMTP_PORT`                  | Нет             | SMTP-порт для локальной среды. По умолчанию `1025`                             |

## Тестирование проекта

### Соглашение по именованию и качеству тестов

#### Соглашение по именованию (Бизнес-ориентированность)
Имя тестового метода должно описывать **конкретный бизнес-сценарий и ожидаемый результат**, а не просто повторять техническое имя функции в коде.

В проекте допускаются два стиля написания (для сохранения обратной совместимости с параллельными ветками разработки):
1. **Компактный стиль с разделением по фазам:** `[Условие/Сценарий]_[ОжидаемыйРезультат]` через нижнее подчеркивание.  
   *Пример:* `void invalidEmail_throwsException()` или `void customerNotFound_returns404()`
2. **Классический CamelCase-стиль:** Начинающийся с префикса `should...`.  
   *Пример:* `void shouldThrowExceptionWhenEmailIsInvalid()`

#### Золотое правило: Тест обязан уметь падать!
Написание теста считается завершенным только после его **проверки на временную поломку кода (фальсифицируемость)**:
1. Напишите тест и убедитесь, что он проходит успешно (зелёный).
2. Перейдите в тестируемый компонент бизнес-логики и **временно внесите дефект** (закомментируйте валидацию, измените возвращаемый статус, удалите вызов сохранения в БД).
3. Запустите тест снова. Он **обязан упасть по осмысленной причине** с понятным текстом в `AssertionError`. Если тест остался зелёным при сломанном коде — перепишите проверки (`assertions`).
4. Верните код в исходное рабочее состояние.

### Уровни тестирования и их запуск

Мы разделяем тесты на быстрые (Unit/ArchUnit) и тяжелые (Integration). Благодаря настроенным Gradle-плагинам тесты разделены по маске имени файлов: модульные тесты заканчиваются на `Test`, интеграционные — на `IT`.

#### 1. Модульные и архитектурные тесты (Unit / ArchUnit)
*Что тестируют:* Изолированную бизнес-логику, мапперы, утилиты, а также соответствие кодовой базы правилам архитектуры пакетов (через ArchUnit). Проходят моментально без поднятия контекста Spring и Docker.
* Запуск через терминал (запускает всё, кроме `*IT.class`):
  ```bash
  ./gradlew test
  ```

#### 2. Интеграционные тесты (Integration / IT)
*Что тестируют:* Взаимодействие компонентов, контроллеры, репозитории. Используют реальную базу данных в Docker-контейнере через **Testcontainers**.
*Оптимизация производительности:* Контейнер базы поднимается ровно один раз на всю сессию JVM. Перед каждым методом срабатывает быстрая очистка таблиц через Hibernate-метамодель (`TRUNCATE CASCADE`), что исключает протекание данных между тестами.
*Требования:* На машине должен быть запущен **Docker Desktop / Colima / OrbStack / Podman**.
* Запуск через терминал (изолированный запуск тяжелых тестов):
  ```bash
  ./gradlew itTest
  ```

#### 3. Полный цикл проверки проекта (включая Jacoco-покрытие от 80%)
Выполняет сборку проекта, все виды тестов, проверки Checkstyle, SpotBugs и верификацию покрытия кода.
* Запуск через терминал:
  ```bash
  ./gradlew check
  ```
### Миграции базы данных
## Миграции базы данных

Схема базы данных управляется только через миграции Flyway. Автоматическое создание или изменение таблиц средствами Hibernate запрещено.

Для Hibernate используется режим `ddl-auto: validate`: при запуске приложения схема только проверяется на соответствие ожидаемой.

### Именование миграций

Миграции именуются по времени их создания:

```text
VYYYYMMDDHHMM__description.sql
```

Например:

```text
V202609151501__create_base_schema.sql
```

Для миграций не используется сквозная нумерация (`V1`, `V2`, `V3` и т. д.), чтобы избежать конфликтов при параллельной разработке.

### Неизменяемость и порядок миграций

Миграция считается **введённой в проект**, когда её файл попал в `main`. Это не означает, что она уже применена ко всем существующим базам данных.

При параллельной разработке миграция с более ранним timestamp может попасть в `main` позже миграции с более поздним timestamp. Поэтому включён режим `spring.flyway.out-of-order: true`: если такая миграция ещё не применена конкретной БД, Flyway применит её при следующем запуске, даже если более поздние миграции уже были применены.

Например:

```text
main содержит:

V202609151501__create_base_schema.sql
V202609151400__add_something.sql
```

Если БД уже успела применить `V202609151501`, то при следующем запуске
`V202609151400` будет применена как `out-of-order`.

**Важно:** после попадания миграции в `main` её файл нельзя изменять или удалять. Если требуется изменить уже введённую схему, создаётся новая миграция с новым timestamp.
